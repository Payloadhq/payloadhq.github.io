x402 payment errors: causes, checks, and fixes

An x402 payment can fail at four different layers: the challenge the server issued, the wallet that tried to pay, the facilitator that verified and settled it, or the settlement itself. Each layer leaves different evidence. This guide maps the errors you will actually see to the layer that produced them, and gives the safe next step for each.

Start with the layer, not the error

  1. Challenge. The server’s 402 response defines what it will accept: amount, asset, network, scheme, recipient. Most “payment” bugs are really challenge mismatches: a stale challenge, the wrong network, an amount that changed.
  2. Wallet and signing. The client builds and signs the payment payload. Wrong fields, an expired allowance, or an invalid signature fail here, before any money moves.
  3. Facilitator verify and settle. The facilitator checks the payload against the challenge and submits settlement. Its error codes, below, are the most precise evidence in the whole flow.
  4. Settlement. The on-chain transaction itself. Settlement can succeed while delivery fails, and can still be in flight while a retry is already asking again.

Facilitator error codes

These codes come back from facilitator verification and settlement. Treat the exact response body as evidence: capture it before you change anything.

CodeWhat it meansSafe next step
insufficient_fundsThe paying wallet does not hold enough of the asset, or of the gas token, on the required network.Check the wallet balance on the exact network named in the challenge. Fund it, or pay a resource priced within the balance. Do not retry unchanged.
invalid_payloadThe payment payload does not match what the server asked for: wrong fields, wrong encoding, or a payload built for a different challenge.Rebuild the payload from the current challenge response, never from a cached one.
invalid_networkThe payment was attempted on a network the server does not accept for this resource.Pay on the network named in the challenge. Similar names are different networks: base and base-sepolia settle in different places.
invalid_schemeThe payment scheme, for example “exact”, is not one the server supports for this resource.Use a scheme listed in the challenge’s accepts array.
amount_too_lowThe amount offered is below the price the server requires.Pay the amount stated in the challenge. Prices can differ per resource and change over time.
kyt_risk_detectedThe facilitator’s risk screening rejected the transaction.This is a compliance stop, not a bug. Do not retry with variations. Use a different funding source, or take it up with the facilitator.
preflight_validation_failedThe facilitator’s pre-settlement checks failed: allowances, signatures, or payload consistency.Re-check token allowances and signature validity, rebuild the payload from a fresh challenge, and retry once.
settle_exact_failed_onchainVerification passed, but the on-chain settlement transaction failed.Confirm the settlement status on-chain before paying again. A second payment sent without that confirmation is how double payments happen.

An unrecognized code is still evidence. Read it as a payload problem first: rebuild from a fresh challenge, confirm the network and scheme, and only then suspect the server.

The v1 / v2 header mismatch

x402 version 1 clients send the payment in the X-PAYMENT header. Version 2 uses PAYMENT-SIGNATURE, with PAYMENT-REQUIRED and PAYMENT-RESPONSE on the other side of the exchange. A v1 client paying a v2 server, or the reverse, produces a payment the other side never reads. The retry still returns 402, the money may even settle, and it looks as if the payment vanished. Before debugging anything else, confirm which header your client sends and which header the server reads.

Paid, but still blocked

A settled payment and a delivered resource are two different events. If the retry raced the settlement, or the proof was attached to a stale challenge, the server answers 402 again. The rule that prevents almost every double payment in this flow: confirm settlement before paying twice. Payload’s paid and blocked guide walks through the four failure modes and the checklist to work before paying again.

The eight codes above are the generic ones. The facilitator also returns scheme-specific codes, and developers paste those long strings into search exactly as they appear. Here is the complete set the CDP Facilitator returns in practice, each with its layer and safe next step. Meanings follow the Coinbase Developer Platform x402 troubleshooting reference, checked November 10, 2026. Layer, next step, and retry guidance are Payload's. invalid_exact_svm_payload_transaction_ — About twenty variants share this prefix; the suffix names the specific instruction or account at fault. Treat the suffix as the diagnosis: rebuild the transaction correcting the named element, and simulate locally before resubmitting.

invalid_batch_settlement_evm_ — The batch-settlement scheme defines its own family under this prefix. The suffix names the failing element of the batch; the verify-then-settle checks in this table apply the same way.

invalid_upto_svm_ / settle_upto_svm_ — The upto scheme on Solana defines invalid_upto_svm_ codes for payment requirements, payload, channel, and settlement failures, plus settle_upto_svm_ codes for onchain and confirmation failures. Settlement-prefixed codes follow the same rule as the other settle_ codes: confirm the transaction before paying again.

Questions

My payment went through but the API still returns 402. Why?

Settlement and delivery are two different events. If the retry raced the settlement, or the payment proof was attached to a stale challenge, the server answers 402 again even though the money moved. Confirm the settlement on-chain or with the facilitator before paying a second time, and check for a v1/v2 payment header mismatch.

Is it safe to retry a failed x402 payment?

Retrying the request is always safe. Sending a second payment is not, until the first payment’s settlement status is known. Most double payments in x402 flows come from paying again while the first settlement was still in flight.

What is the difference between the X-PAYMENT and PAYMENT-SIGNATURE headers?

X-PAYMENT is the x402 v1 header; PAYMENT-SIGNATURE is the v2 header. A v1 client paying a v2 server (or the reverse) produces a payment the other side never reads, so the retry still returns 402 and it looks as if the payment vanished.

Which x402 error codes come from the facilitator?

Codes such as invalid_payload, preflight_validation_failed, settle_exact_failed_onchain, and kyt_risk_detected are issued during facilitator verification and settlement. Challenge-layer problems usually appear as a fresh 402 with a new payment challenge instead of an error code.
